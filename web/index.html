Section 1

Spatial routing: a deterministic line-probe router, validator-last

Representation. Obstacles are axis-aligned boxes inflated by clearance + the duct's half-extent in the bend plane: a conservative Minkowski sum (a box, not a rounded box). A 45° diagonal that leaves an inflated corner keeps margin·√2 ≈ 0.21 m from the real corner, so the box is safe for diagonals too. Everything is snapped to and compared at millimetres, so "exactly 15 cm" is a clean pass rather than a rounding accident.

Why a geometric offset and not a search. Ducts are axis-aligned with 45°/90° fittings, and a moved beam is one blocker on a straight run. For that case an analytic line probe (the Hightower / Mikami–Tabuchi family of routers) is exact, deterministic and sub-millisecond. Every candidate side carries an explicit feasibility test, and when none passes the answer is NO_ROUTE with a reason the platform turns into a coordination issue for structural: a sleeve through the beam, a local bulkhead, or moving the beam. A coordination tool has to say why there is no route.

Feasibility, under the beam: z = beam_bottom − clearance − h, feasible iff z − h − c_ceiling ≥ Z_c. Try it above: switch to the 400×300 duct and turn the ceiling on at 2.40 m. The real duct's bottom sits at 2.07 m, so the route is only feasible with the ceiling below 2.05 m.
Geometric offset (line probe)
< 1 ms · deterministic
Chosen for the one-blocker case. 45°/90° fittings by construction, exact clearance, stable ties. One obstacle per probe.
Sparse orthogonal graph + A*
1–30 ms (est.)
The generalisation for many obstacles: nodes only at inflated face coordinates, state = (node, direction) with a turn penalty, then a chamfer pass turns Z-steps into 45° offsets.
A* on a 5 cm voxel grid
50 ms – 2 s (est.)
800k voxels per 10 × 10 × 1 m zone; staircase paths need smoothing; resolution fights clearance accuracy; turn cost needs direction state.
3-D visibility graph
ms · arbitrary angles
Shortest path among 3-D polyhedra is NP-hard; the vertex graph is a heuristic, and its angles are not duct fittings.
RRT*
100 ms – s · sampled
Non-deterministic, needs smoothing, built for high-DOF kinematics. Not for ducts.

The whole algorithm (Python in the repository, JavaScript on this page)

reroute(run, obstacles, c):
    box = first obstacle whose inflated box the straight run penetrates
    if box is None: return straight
    for side in (under, over, left, right):        # fixed order = stable tie-break
        inf    = box.inflated(c.clearance + run.section.half_in_plane(side))
        target = inf.face(side);  d = |target - run.level|
        lead   = d if c.bend == 45 else 0
        pts    = [A, A.at(inf.entry - lead), (inf.entry, target),
                  (inf.exit, target), B.at(inf.exit + lead), B]
        if not feasible(side, target, ceiling, soffit, zone,
                        other_obstacles, min_straight): note reason; continue
        cost[side] = length(pts) - |AB| + 0.25 * bends(pts)
    best = argmin(cost) or NO_ROUTE(reason of the preferred side)
    assert validate(best.pts) == []                # the gate's rules, on ourselves

Cost. Added length plus 0.25 m per fitting (a fitting costs a pressure drop and a hanger, not only duct). Ties break in the order under, over, left, right, so the same input always gives the same route; a deterministic engine is what makes the audit record in section 3 meaningful.

Gravity systems. A drain may never rise, so "over" is refused outright and a route under the beam is returned as needs_review: the drop propagates downstream and the whole run has to be re-sloped at ≥ 1 %. The proposal lists the affected elements rather than pretending the problem is local.

With more time. The second tier runs only when the probe meets a second obstacle: a sparse orthogonal graph on the inflated face coordinates, A* with a turn penalty, and a deterministic chamfer pass so both tiers emit the same fitting style. Both end in the same validator.

Section 2

Real-time data flow: a 40 cm beam move, Revit-native

Capture, in the plugin. Application.DocumentChanged fires after the architect's transaction commits. Filter to geometric categories and the primary design option; compare Element.VersionGuid plus a bounding-box hash so parameter edits are dropped. One transaction is one ModelDelta, applied atomically to the twin. No debounce: a move is one transaction; coalesce only while a delta for the same element is in flight. Feet become metres through UnitUtils; shared coordinates through ActiveProjectLocation.GetTotalTransform(). Identity is {modelId}:{UniqueId}, version is VersionGuid. Our own accepted-proposal transactions are recognised by name and never echoed back.

Linked models. The beam lives in the structural RVT, which the mechanical engineer sees as a link that updates only on reload. The twin bridges that gap: a ghost of the moved beam and the rerouted duct appear before the reload, and the proposal is re-validated against the authoritative geometry after it. DocumentChanged gives a live preview proposal; DocumentSynchronizedWithCentral a committed one.

Transport. WebSocket with protobuf or MessagePack for both desktop and web. Revit add-ins are .NET Framework 4.8 sharing one AppDomain, where Grpc.Net.Client and Google.Protobuf clash with other vendors' add-ins and HTTP/2 bidirectional streaming needs WinHttp on Windows 11; grpc-web has no client streaming. gRPC stays service-to-service inside the cloud.

Cloud. Gateway with project-scoped tokens, then NATS JetStream partitioned by project (a zone is a fan-out concern, not an ordering key), then the spatial engine. The twin is a materialised view of the event log: bounding volumes and centre-lines, about 100 bytes per element, 50k elements ≈ 5 MB, rebuilt from the log on failover. Update the beam in O(log n), query the runs intersecting old ∪ new inflated boxes, reroute, validate, append a RoutingProposal. At-least-once delivery with an idempotent consumer keyed by (id, VersionGuid). One beam affecting 200 runs becomes one ChangeImpact, pushed to the mechanical engineer and to the architect: "your move affects 3 runs" is the most valuable real-time signal in the product.

Apply, in the plugin. An ExternalEvent draws the proposal as a DirectContext3D overlay; nothing is edited until the engineer accepts. Accept is a compare-and-swap on the proposal's read-set {elementId: VersionGuid} (beam, duct, other obstacles); otherwise STALE_VERSION and a fresh request. On reconnect the plugin replays its outbox from the last acknowledged sequence, or takes a zone snapshot if the log was compacted.

Why nothing freezes. Deltas under 1 KB, never models of 100 MB to 2 GB. The heavy model never leaves the client. An overlay, not an edit. One impact message, not N pushes. An incremental index.

Section 3

AI safety gate and the API contract

The guarantee comes from what the model may output. The pattern model emits cost weights or a ranking over deterministic candidates, never geometry, so even its best output is a route the router built and validated. In the weaker mode, candidate waypoints in a strict JSON schema, the same validate() runs: clearance with the duct body, ceiling clearance measured on the duct bottom, gravity slope (monotonic, ≥ 1 %), bends in {45°, 90°}, minimum straight, soffit, zone, endpoints. A failure triggers a bounded deterministic repair (push each waypoint out through the nearest inflated face, three passes) and a re-check; if that still fails, the deterministic route is used. Every decision writes an audit record. Shadow mode first, a kill switch, and property tests: random obstacles plus random perturbations give zero accepted violations.
